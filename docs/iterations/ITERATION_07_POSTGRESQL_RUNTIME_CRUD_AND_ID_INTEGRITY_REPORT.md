## 4. Problems Addressed

A. Generated code had been compiled but not executed against PostgreSQL.  
B. Blank or duplicate canonical IDs could reach `Map`-based relation preparation.  
C. Frontend readiness and backend authority intentionally duplicate capability rules and needed an explicit conformance contract.

## 5. Canonical ID Rules

- Model id: non-empty after trim.
- Class ids: non-empty and unique among classes.
- Attribute ids: non-empty and unique among all model attributes.
- Relationship ids: non-empty and unique among relationships.
- IDs remain opaque; no UUID format is imposed.
- Class, attribute, and relationship IDs use separate namespaces. The same text may appear once in different namespaces.

## 6. CU08 ID Validation

CU08 now emits error diagnostics:

- `MODELO_ID_REQUERIDO`
- `CLASE_ID_REQUERIDO`, `CLASE_ID_DUPLICADO`
- `ATRIBUTO_ID_REQUERIDO`, `ATRIBUTO_ID_DUPLICADO`
- `RELACION_ID_REQUERIDO`, `RELACION_ID_DUPLICADO`

No ID is repaired or generated by the validator.

## 7. Backend ID Defense

CU09 validates identity before building any class/relation map. Blank and duplicate IDs produce `ErrorModeloNoGenerable`; the Express boundary therefore returns HTTP 400 rather than 500. Tests also prove that using the same textual ID in the class and relationship namespaces is allowed.

## 8. Generation Capability Profile

The concise capability contract is [`docs/generation/SPRING_GENERATION_PROFILE.md`](../generation/SPRING_GENERATION_PROFILE.md). It documents concrete/scalar independent entities and exactly `asociacion 1 ↔ 0..*` as supported, while preserving all Iteration 06 exclusions.
